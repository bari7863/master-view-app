Master Data App — Integrated System Roadmap

企業マスタ管理から、営業・マーケ統合基盤への拡張ロードマップ

現状は「企業マスタ管理＋クローリング」に特化した基盤。ここにSFA・CRM・MAの機能群を積み上げ、一元管理システムへ拡張するための、着手順とその理由をまとめる。

結論

最初に着手すべきは Phase 0: データ基盤の拡張 と、それに続く Phase 1: CRM基礎（顧客・活動管理）。 理由は単純で、既存の企業マスタと権限管理の資産をそのまま延命でき、営業が最短で使い始められるのがこの2つだから。 メール自動配信・スコアリングなどMA領域は技術難度と外部連携が重く、データが溜まった後でないと機能として空箱になるため、後半フェーズに置く。

Roadmap

下にいくほど、依存する前提データ・機能が増える。前段が薄いまま次に進むと、機能を作っても使われない／データが埋まらない状態になりやすい。

データ基盤の拡張整備

最優先・土台

企業マスタ1本の構造を、複数機能が乗せられる形に広げる

やること

  • 企業マスタに紐づく「担当者」「活動履歴」「案件」テーブルの設計
  • 権限キー体系を新機能にも拡張できる形に一般化
  • Neon / Supabase 双方への同一スキーマ適用ルール整備

既存資産との接続

  • 企業ID（既存マスタの主キー）を全新規テーブルの外部キーにする
  • lib/master-data-permissions.ts の権限判定ロジックを再利用
  • DB切替の仕組み（選択中DBのみ参照）をそのまま踏襲
優先理由：ここを飛ばして機能を先に作ると、後から全テーブルにDB切替・権限制御を後付けすることになり、手戻りが一番大きい。土台は最初の1回で正しく広げるのが最も安い。

CRM基礎：顧客管理

早期着手

企業マスタの「上」に、人・接点の情報を乗せる

やること

  • 企業ごとの担当者情報（氏名・部署・連絡先）管理
  • 電話・メール・訪問などの接点履歴（活動ログ）記録
  • 企業単位のメモ・タグ付け

既存資産との接続

  • クローリングで取得済みの代表者名・電話番号・メールアドレスを初期値として活用
  • 権限管理で「自分の担当企業のみ閲覧」等の絞り込みを追加
優先理由：新規テーブル1〜2個で完結し、権限管理への影響が小さい。既存の「テレアポ・フォーム営業に使う」という利用実態に一番近く、営業が翌日から使える価値が出る。

SFA：案件管理・行動管理・予実管理

中核

営業プロセスそのものを可視化・管理する

やること

  • 案件（商談）のステータス・金額・確度・担当者管理
  • 架電・訪問・メール送信などの行動記録とタスク管理
  • 目標設定と実績集計（予実管理）のダッシュボード

既存資産との接続

  • Phase 1の活動履歴に「案件」を紐付けるだけで商談管理化できる
  • 担当者ごとの権限（自分の案件のみ操作可）を権限管理に追加
優先理由：CRM基礎（担当者・活動ログ）がないと案件管理は「誰が何をしたか」が紐付かず機能しない。逆にCRMさえあれば、案件テーブルを1枚足すだけで一気に営業支援システムらしくなる。

データ分析・ダッシュボード

データが溜まってから

案件化率・稼働・成約傾向を見える化する

やること

  • 担当者別・企業属性別の成約率、案件化率の集計
  • クローリング精査状況（欠損率・候補反映率）の可視化
  • 経営層・マネージャー向けサマリー画面

既存資産との接続

  • Phase 1・2で蓄積した活動履歴・案件データを集計元にする
  • 権限に応じて見える集計範囲を制御（自部門のみ等）
優先理由：分析はデータがあって初めて意味を持つ。案件・活動データが空の状態で先に作ると、グラフが空のまま使われない機能になる。

MA基礎：メール／フォーム自動配信

技術難度：中〜高

クローリングで集めた接点情報を配信に活かす

やること

  • メールテンプレート作成・一斉配信・配信予約
  • 取得済み問い合わせフォームURLへの自動送信（フォーム営業の自動化）
  • 配信対象リストの絞り込み（権限・フィルタ条件の流用）

既存資産との接続

  • クローリングで取得済みの「メールアドレス」「フォームURL」がそのまま配信先データになる
  • フォーム誤取得（採用応募フォーム等）対策は既存クローリング精度ルールを流用
送信ドメイン認証・迷惑メール規制・フォーム自動入力のブラウザ制御など、外部連携の技術難度が他フェーズより高い
優先理由：既存データ資産（メール・フォームURL）との相性は最高に良いが、外部送信という後戻りしにくい領域なので、CRM/SFAで運用が安定してから着手する方が安全。

行動履歴分析・スコアリング

MA配信基盤が前提

配信・閲覧データをもとに見込み度を数値化する

やること

  • メール開封・クリックの追跡
  • フォーム送信・サイト訪問などの行動ログ収集
  • 行動データに基づくリードスコアリング

既存資産との接続

  • Phase 4の配信ログがそのままスコアリングの入力データになる
  • スコア上位企業をSFAの案件優先度に反映
優先理由：配信基盤がないと追跡すべき行動自体が発生しない。Phase 4が育って初めて価値が出る、完全な後続機能。

カスタマーサポート

独立性高・最後で可

問い合わせ対応・FAQなど、営業活動から独立した領域

やること

  • 問い合わせ管理・対応履歴
  • FAQ・ナレッジ管理

既存資産との接続

  • 企業マスタ・担当者情報は流用できるが、業務フローは営業系と別立て
優先理由：現行アプリの主目的（営業リスト精査・フォーム営業）から最も遠く、他機能ほど既存資産と噛み合わない。ニーズが明確になってから着手で問題ない。

Constraints

全フェーズを通じて、既存CLAUDE.mdの運用ルール上、必ず守る前提。

権限管理
新機能を追加するたびに権限キーを拡張。画面側の非表示だけでなく、必ずAPI側でも制御する。既存ユーザーの権限初期値は変えない。
DB分離
新テーブルもNeon / Supabaseで完全分離。選択中DBのデータのみ参照・保存し、両DBのデータを混在させない。
クローリング精度
CRM・MAで既存のクローリング取得値（代表者名・電話番号・メール・フォームURLなど）を再利用する際も、取得精度を落とす変更は行わない。
既存機能
一覧・フィルタ・CSV入出力・クローリング・ログインなど現行機能への影響がないか、新テーブル追加のたびに確認する。

次の一手

まずPhase 0のデータモデル設計（担当者・活動履歴・案件テーブルの設計と権限キー拡張方針）から着手するのが最短ルート。

1企業マスタに紐づく新テーブル群のスキーマ案を作成（Neon / Supabase 両対応）
2権限管理の権限キー体系を、CRM/SFA機能を見越して拡張設計
3Phase 1（顧客管理）の画面・APIを既存 app/page.tsx 権限フローに接続
